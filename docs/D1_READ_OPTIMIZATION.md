## 问题与修改

负责人提供的 SQL Insights 截图显示，来源列表的两种相关子查询累计读取约17.25M/40次和1.6M/3次。截图未显示时间窗口，不将这些累计量当成每日用量。默认列表此前已改用当前页批量计数，但其已发布统计仍多次展开公开视图；按文章数排序和单个来源详情仍使用原相关计数。

- `source-counts.ts` 先按选中来源的索引取得“来源—文档”对，用 UNION 去除主来源与重复出处的重叠。文章数排除有效清理墓碑；已发布数独立按文档主键检查原 `console_public_documents` 视图。
- 普通来源列表只统计当前页；文章数排序先对全部符合筛选的来源批量计数，再排序分页，已发布数只计算返回页。来源详情复用相同统计逻辑。
- 雷达/校园知识的分组首屏使用同一条查询取得各分类总数及前若干文章，减少一次公开视图扫描。
- 按 ID 读取单篇元数据时直接使用 `d.id=?`，避免可选参数 OR 条件妨碍主键查找。

公开视图、来源许可、发布批准、版本、生命周期和暂停/撤回检查继续由现有 SQL 执行；未加入公共内容缓存。没有新增索引依赖。

上述为部署前1日累计快照，不代表每日固定用量。实施的代码变化是：

- 新增迁移0039并仅应用于Preview：`document_origins(source_id,document_id)`、官方文章来源/日期表达式、URL、清理项、session/revoked-token/限流桶清理、公众号文章聚合、回执日期和首版本日期索引。
- 来源指定的文章列表改为先物化主来源及出处文档ID集合，避免`source_id OR correlated EXISTS`使数据库从全文章表筛选；按来源+日期表达式索引取候选。
- 公众号后台把文章总数、下架数、最后观察时间从三个相关子查询合并为一次有覆盖索引的物化扫描，并把墓碑检查每文章只求一次。
- 总览统计不再对所有范围内文章逐篇运行`min(receipt)`与首版本查找。它只从日期范围的回执/首版本记录定位首次导入，并从活动保护集合反向生成受保护文档集合。
- 带来源文字筛选的分类计数先物化匹配来源ID，再读这些来源的公开文章。
- 官网手动采集用统一`manual:`前缀登记并设置`manualOverride`；修复全站请求未登记错误。该项影响任务功能，不纳入Rows read降幅。
