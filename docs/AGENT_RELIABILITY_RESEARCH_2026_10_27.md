# CampusOS Agent 可靠性工程依据

查阅日期：2026-10-27。本文只做官方资料调研和代码对照，未改运行代码、部署或读取凭据。以下“官方建议”和“CampusOS 落实建议”分开；建议不等于已实现、已训练或已验收。

## 一、官方资料给出的流程

Anthropic 区分预定义代码路径的 workflow 与由模型决定步骤的 agent，建议从简单、可组合方案开始，复杂度应有评测收益支撑。已知步骤可固定，开放问题再让模型规划；不是所有环节都必须依赖模型临场生成工具调用。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

OpenAI 的优化流程先建立评测基线，再调整指令及上下文，必要时才微调，修改后重跑代表性测试。持续变化的校园事实应实时检索，不能靠模型记忆补齐。[Model optimization](https://developers.openai.com/api/docs/guides/model-optimization)

Anthropic 建议可从真实失败提炼20—50个初始任务；同时覆盖应调用与不应调用工具的情况，并用多次试验观察不确定性。最终状态、程序评分和人工复核要结合，不能把一句“完成了”当成功。[Agent evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

OpenAI 建议先检查完整轨迹定位工具、路由或交接问题，再建立可重复的数据集与评测运行；不只看最终答案是否含关键词。[Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)、[Trace grading](https://developers.openai.com/api/docs/guides/trace-grading)

## 二、CampusOS 应怎样分工

以下是针对当前项目的工程推论，不要求更换框架、供应商或购买服务：

- **模型**：理解意图、必要的查询改写和证据综合；不充当实时事实库。
- **Prompt/人格**：定义目的、语气、示例及沟通方式；不替代检索和权限判断。
- **RAG**：提供当前允许公开的真实正文与版本依据；召回命中不等于事实已充分证明。
- **Tools**：封装真实检索、网页读取和地图能力，验证参数、权限、超时与输出。
- **编排**：维护任务、约束、执行状态和失败类型；明确请求的步骤可以确定性路由，复杂任务保留模型规划。

人格应与业务事实、证据和工具规则分层。OpenAI 将身份、指令、示例、上下文区分组织；Anthropic 强调同时管理工具、历史和外部数据，避免把大量边缘案例堆入Prompt。[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)、[Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**落实建议**：人格可改变措辞与解释风格，但不能改变时间窗、来源等级、预算或工具权限，也不能把“不知道”演成“知道”。同一组事实与工具测试应在各人格下重复；本调研没有读取或评价人格仓库。

## 三、当前故障与可执行验收

当前代码观察不是完整故障根因证明：

| 故障                        | 代码线索                                                                                                | 应验收的行为                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 明确要求小红书却未查询      | `external-search/skill.ts`在events分支排除原生小红书；`policy.ts`的近期活动匹配不覆盖“这一周发生的趣事” | 查看真实轨迹的来源选择、查询参数、调用结果；不能用网页结果冒充原生搜索                       |
| 旧事说成本周                | `content-intent.ts`只给关键词/工具名；时间条件仍可能由模型自由填写                                      | 服务器解析上海时区与日期区间，区分发布日期、实际活动日及报名日；未知发生时间不得说成本周发生 |
| 辱骂被当名字、“666”触发失败 | `intent.ts`短汉字澄清条件未区分纯反馈；其他短消息仍可能进入模型工具流程                                 | 识别请求、反馈、确认、闲聊；纯反馈不替换原任务主题，不触发检索或假称已重查                   |

建议依次执行：

1. **冻结基线**：保留当前版本与失败轨迹，先纳入截图原句、措辞变体、多轮追问和闲聊反例。
2. **分层定位**：先独立检验工具返回真资料，再检验编排，最后检验回答。每条轨迹记录模型/Prompt版本、解析约束、调用来源、工具名及有界参数、状态、引用、耗时、token、D1行数；不记录密钥或私有全文。
3. **小步修复**：一次改变一个流程变量。程序路由必须标成server-routed，模型发起的调用另标，不伪造模型轨迹；确定性不等于硬编码事实答案。
4. **双层回归**：固定工具夹具用于稳定离线评测，少量真实Preview请求验证集成；两者分报。检查答案依据、时间匹配、工具使用及原有地图/知识/雷达不回归。
5. **发布闸门**：本次关键失败用例全部通过、应不调用工具的反例也通过，并人工抽查引用。阈值是项目建议，不能用一次成功或大量无关单元测试代替可靠性结论。

最低案例应包括：近七天资讯、本周已发生事件、未来活动、仅发布日期可用、过期报名、指定小红书、官方截止日期、同一主题追问、纯辱骂/感谢/“666”、网络故障、来源登录失效、空答及模型截断。可接受多种合理工具路径，但来源、日期、权限等明确约束必须满足；评测应同时看结果和必要轨迹。[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 四、什么时候真正训练模型

SFT使用优质示范输入/输出改善稳定行为；应先有独立评测集，再判断训练是否优于基线。DPO使用同一输入下优选/劣选回答对，适合表达偏好。[SFT](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)、[DPO](https://developers.openai.com/api/docs/guides/direct-preference-optimization)

**当前推论**：网络失败、来源未执行、日期未绑定和反馈误路由先修数据与编排。工具可靠、任务定义稳定后，若大量独立样本仍呈现相同的指令/格式或人格表达问题，才积累清洁数据，分离训练/验证/留出测试，再考虑微调。不能用实时新闻训练记忆，或把错误轨迹直接当示范。

本文引用训练方法，不代表现有Step/DeepSeek套餐提供相应训练接口；支持、许可与费用尚未核验。所引OpenAI优化/微调页面已有平台迁移或退役提示，不能据此新建依赖。本轮保持原Agent、Step优先/DeepSeek后备，不发起训练或部署。
