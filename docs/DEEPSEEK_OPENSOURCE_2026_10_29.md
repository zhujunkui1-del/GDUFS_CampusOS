# DeepSeek 开源资料能否直接用于 CampusOS 检索（2026-10-29）

负责人要求把 https://github.com/deepseek-ai 的开源资料直接接到 Agent 上，一劳永逸解决检索不稳定、查询扩展、同义词、提示词约束、意图过滤和只拿到标题摘要的问题。先把事实核清。

## 该组织实际开源了什么

核对 GitHub 组织仓库（2026-10-29）：

| 仓库 | 内容 | 对本项目检索的作用 |
| --- | --- | --- |
| `DeepSeek-V3` / `DeepSeek-LLM` / `DeepSeek-Math` / `DeepSeek-VL` | 模型权重与推理代码 | 需要 GPU 托管；Workers 无法运行 |
| `DeepSeek-OCR` | 图像/文档光学压缩与识别 | 可处理扫描件，但同样需要 GPU/容器 |
| `DeepInfer` | 大模型推理框架 | 需要 GPU 集群，与本项目无关 |
| `FlashMLA` / `EPLB` / `ESFT` / `profile-data` | 注意力算子、专家并行、微调与性能分析 | 训练/推理基础设施，不解决检索 |
| `deepseek-harness` | Agent 插件框架（TypeScript） | 是开发工具本身，不是检索组件 |

结论：**deepseek-ai 没有开源可直接嵌入的 RAG、搜索、查询改写或向量检索组件。** 现有仓库是模型权重、推理框架和训练工具；"直接接上"意味着自建 GPU 推理服务，这与本项目"只用 Cloudflare、不购买 VPS/GPU、不新增未批准付费资源"的约束冲突，也不能自动修复检索链路里的工程缺陷。

## 能合法且低成本采用的部分

1. **DeepSeek API 作为主模型**（已完成）：Preview 已切为 DeepSeek 主、Step 备用；可用于查询改写与答案生成，无需自建推理。
2. **DeepSeek-OCR（可选，后续）**：仅在需要解析扫描版通知/附件时评估；需 GPU 容器与费用审批，不是当前瓶颈。
3. **借鉴 `deepseek-harness` 的插件化边界**：把检索 Provider、改写器、证据校验做成可替换模块，而不是继续在 `chat.ts` 里堆逻辑。

## 为什么"换模型"不能解决这些问题

当前故障来自检索与证据管线，不是模型智力：

- 同义词不敏感：D1 是 FTS5 词项/规则检索，没有向量语义；"赛事/比赛"、"门诊楼/门诊部"需要查询扩展或混合检索。
- 只拿到标题/摘要：外部 Provider 返回 `title_only`/短摘要，缺少正文抓取与正文准入。
- 提示词约束没强制执行：需要结构化输出 + 服务端校验，而不是更长提示词。
- 意图过滤漏洞：已修（地图场景与天气上下文串味）。
- 检索不稳定：缺少查询改写、多路召回融合与稳定的证据评分。

换更大的模型只会让"没有证据时编得更像"，不会让 D1 多召回一篇正文。

## 建议的可行改造（需批准资源）

1. **混合检索**：保留 FTS5，新增向量召回（Cloudflare Vectorize + Workers AI `bge-m3` 或等价嵌入），按 RRF 融合；这是解决同义词/语义召回的正解。需新建 Vectorize 索引与嵌入调用，产生费用。
2. **查询改写**：用现有 DeepSeek API 在零命中时生成 2–3 个关键词变体（不新增供应商），复用已实现的同义实体重试框架。
3. **正文准入**：对外部 `title_only` 结果用已有 Browser Run/Exa Contents 抓正文；抓不到就不进入答案。
4. **结构化约束**：最终答案用 JSON Schema（结论、引用编号、URL、时效性）输出，服务端校验后再渲染，替代"靠提示词自觉"。
5. **回归集**：把本次 6 个真实故障句与 113 个地图标注纳入固定评测，按空结果率、引用准确率、回答支持率验收。

## 本轮已做

- 修复地图场景"4号门/贝岗门/B8报告厅"被误判为无关问题；全量 113 个地图标注路由审计 0 遗漏（4 个占位名、2 个重复桥名列为数据问题）。
- 修复校园上下文导致"北京天气"进入检索并泄漏被排除标题；排除提示不再携带任何标题或正文。
- 来源按标题去重；摘录引用统一为 `[n]`；生成温度降到 0.2，降低同一问题两次回答的随机差异。
- 仍未解决：云山学者在模型调用失败时仍会退化为原文摘录（与正常答案不一致）；混合检索未实施，需资源批准。
